# Tidebench：产品方案与反方审视

本文保留 v0.1 开发者预览的原始产品决策与研究过程。v0.2 已扩展到现货／USDT 永续、版本化历史数据、五种研究模式、统一模拟账户、权限与恢复；当前实现以 [README](../README.zh-CN.md)、[研究模型](pro-research.md)和[验收记录](verification.md)为准。下文“当前／首版”指 v0.1，不能用作 v0.2 功能清单。

调研日期：2026-10-08。第一阶段：自托管、单工作区、现货、真实公共行情、历史回测与本地模拟交易。**商业化是产品目标，v0.1 是可运行的开发者预览，不是已获验证的实盘交易系统。**

## 1. 产品应解决什么问题

目标用户是会写一点策略、但不希望长期维护杂乱脚本的独立量化研究者和小型研究团队。他们真正需要的不是更多机器人名称，而是一条可以核查的链路：

**观察市场 → 定义假设 → 含成本的回测 → 检查结果与数据 → 相同策略的前向模拟 → 审查交易与风险。**

首版的北极星指标是“一个新用户能否在不提供密钥的情况下完成这条研究闭环，并解释每笔模拟成交”。增长指标可以记录首次完成回测率、结果导出率、七日再次研究率；没有实现遥测之前，不对外声称用户留存或转化数字。

## 2. 研究后的定位取舍

[Freqtrade](https://github.com/freqtrade/freqtrade) 已有交易所接入、回测与 dry-run；[Hummingbot Dashboard](https://github.com/hummingbot/dashboard) 已覆盖策略管理和部署。因此，“支持 OKX”与“有漂亮图表”都不足以构成长期壁垒。

我们选择 **inspectable research**：每次结果保留输入快照、数据哈希、版本、参数、成交假设与完整流水；复现应不依赖当时交易所仍返回同一历史内容。这个方向借鉴 [NautilusTrader 的组件边界](https://nautilustrader.io/docs/latest/concepts/architecture/) 与 [QuantConnect 的结果检查工作流](https://www.quantconnect.com/docs/v2/cloud-platform/backtesting/results)，但不声称首版具备它们的市场覆盖或生产成熟度。

商业切入点不是贩卖收益预测。未来可以围绕团队研究协作、受控执行、托管运维、审计与组织治理收费；是否采用这些模式，需要真实访谈与付费试点验证。

## 3. 第一版完整交付边界

| 工作流 | 当前实现目标 | 明确边界 |
|---|---|---|
| 市场观察 | 五个 USDT 现货交易对、四种周期、真实 OKX 数据与来源信息 | REST polling，不是低延迟 WebSocket 终端 |
| 研究 | SMA 趋势、Wilder RSI 均值回归、买入持有模板 | 教学与研究模板，不宣称盈利 alpha |
| 回测 | 下一根开盘成交、双边费率、滑点、精度、持仓与权益、基准 | OHLCV 市价模型，无盘口冲击/队列/衍生品 |
| 复现 | 持久化 run、输入快照、哈希、JSON 导出、离线 replay | 交易所历史内容可能修订；保留的是当次观察 |
| 前向模拟 | 分来源账户、手动模拟成交、自动策略监督器、账本与审计 | 本地 paper，不是 OKX Demo，也不发送真实订单 |
| 风险 | 每单限额、单资产占比、观察日损失限制、持久化 halt | 不是外部独立风控进程；不自动清仓 |
| 部署 | Python 后端、React 前端、锁定依赖、Docker 与 CI | 单工作区、单进程，不提供多租户承诺 |

## 4. 从用户视角设计界面

界面是研究工作台，不是营销落地页。首屏让用户立即看到交易对象、周期、来源与图表。采用冷白画布、墨色文字、克制的柑橘色主操作；通过排版、留白、数据对齐和内容层级建立结构，避免给每块内容包裹描边卡片。

五个工作区分别处理：市场总览、策略研究、模拟交易、风险与活动、设置。参数在研究对象旁编辑，结果和假设保持相邻；模拟账户始终显示 Local paper，合成数据始终显示 Example/Synthetic。来源和执行环境是两个不同维度，不能用一个绿色 LIVE 标签混淆。

桌面以侧边导航、大面积图表和精简 inspector 组织内容；手机按状态、图表、主要动作、结果顺序改为单列。键盘焦点、错误原因、空状态、重试和加载是主流程的一部分。颜色之外还用正负号与文字表达盈亏与状态。

图表使用 [Lightweight Charts](https://tradingview.github.io/lightweight-charts/docs/5.0)，保留 TradingView attribution 与 NOTICE。选择它是为了适合交互式金融图表及明确的开源许可，而不是复制其他产品界面。

## 5. 必须挑战自己的假设

| 反方问题 | 结论与实际应对 |
|---|---|
| “是不是又一个 AI 生成的 dashboard？” | 只保留有后端行为的控件；参数真的参与计算，订单真的进入持久账本；用浏览器端到端验证。 |
| “回测高收益是否来自未来函数？” | close(t) 只能在 open(t+1) 成交；做 prefix/未来扰动测试；最后一根信号不回填。检测范围仍有边界。 |
| “手续费一加就失效怎么办？” | 成本是显式输入与报告字段；不隐藏失败、不挑选漂亮案例；后续增加批量成本压力测试。 |
| “Sharpe 看起来很高就可靠吗？” | 少于 30 个完整 UTC 日收益不给 Sharpe；满足阈值也不代表显著性或未来表现。 |
| “重复点按钮会多买一次吗？” | 永久幂等键、数据库唯一约束、同事务更新账本；同键不同参数拒绝。 |
| “停止按钮真的停止吗？” | halt 与成交在同一写事务检查；停止策略与卖出持仓分离，界面解释各自含义。 |
| “行情断线会自动换假数据吗？” | 明确报错，保留来源语义；示例数据必须由用户显式选择，账户也分开。 |
| “公开 API 就能商业转售吗？” | 不能这样推断；公开代码不打包真实行情，商业托管前单独解决数据授权。 |
| “SQLite 是商业系统的最终架构吗？” | 不是。首版明确单 writer，并用进程锁拒绝共享数据库多实例；团队版采用 PostgreSQL、任务租约与权限隔离。 |
| “界面精致就等于行业顶尖吗？” | 不能。长期运行、恢复演练、独立安全审查、真实用户验证与可量化 SLO 才能支撑更高成熟度声明。 |

[Freqtrade 官方说明](https://www.freqtrade.io/en/stable/lookahead-analysis/) 展示了前视偏差的隐蔽性与检测局限；[PBO 论文](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf) 和 [Deflated Sharpe Ratio 论文](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf) 提醒策略筛选与多次尝试会夸大表现。首版不把这些高级统计方法伪装成已经实现的功能。

## 6. 商业化路线按门槛推进

**阶段 A：当前开发者预览。** 完整本地闭环、真实数据适配、可复现结果、持久账本、风险控制、测试、可安装仓库与准确文档。

**阶段 B：研究专业版。** 更长历史目录、版本化数据集、样本外与 walk-forward、成本压力矩阵、参数邻域稳定性、运行比较、策略插件 SDK。任意用户代码必须先隔离，不能直接在 API 进程执行。

**阶段 C：交易所 Demo 验证。** 独立执行 worker、订单状态机、超时 Unknown、REST/私有 WS 对账、部分成交、手续费资产、时钟偏差、断网与重启演练。至少完成约定的持续运行与恢复验收后，再讨论实盘。

**阶段 D：团队与托管商业版。** OIDC/RBAC、tenant 隔离测试、PostgreSQL、KMS/Vault、任务 fencing、备份恢复、审计保留、运营 SLO、升级兼容、数据授权、事件响应。计费和团队能力不能以“有几个 workspace 字段”冒充完成。

**阶段 E：受控实盘。** 小额、人工批准、明确权限、独立风控、事故处置和长期对账。用户此轮明确选择真实行情、回测和模拟交易，所以当前 release 没有真实下单路径。

## 7. 开源增长策略

使用 English 主 README 与完整中文入口；第一屏给出一句价值、真实产品截图、准确成熟度与启动方法。用能本地复现的动作证明价值，而不是虚构收益、性能或用户数。贡献指南、issue 模板、CI、许可证、变更记录与分阶段 roadmap 降低参与成本。

初始传播材料围绕三个可验证动作：**修改假设 → 查看含成本结果 → replay 同一输入**。发布说明同时写限制与下一步。GitHub topics 帮助发现项目，但没有任何办法保证 star 数量；不采用购买 stars、群发私信或伪造社区信任。对外发帖草稿在 `docs/launch.md`，不自动代发。
